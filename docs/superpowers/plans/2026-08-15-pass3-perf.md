# d9mt Perf Pass 3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cut per-draw CPU in the two measured hot paths — FF cbuffer rename in xform mode (W1) and the app-thread dynamic-VB lock/draw loop in part mode (W2).

**Architecture:** W1 splits the FF VS constants: the three per-draw matrices (WorldView/NormalMatrix/InverseView, 192 B) move from the per-draw-renamed `m_vsFixedFunction` UBO into the FF VS push-constant block (riding the pass-2 push cache); the cold UBO stops renaming per draw via a hot/cold dirty-flag split. W2 attributes the part-mode batch cost with dev-build micro-probes, then applies measured cuts from a bounded menu (lock fast-path first).

**Tech Stack:** C++17, mingw-w64 (i686 PE), vendored DXVK 2.7.1 front-end (`vendor/dxvk/src/d3d9/`), d9mt Metal backend (`src/d3d9fe/`), SPIRV-Cross, bench.c/consttest/spectest/depthbias/resettest harness.

**Spec:** `docs/superpowers/specs/2026-08-15-pass3-perf-design.md` (same repo).

## Push-data layout (post-Task 2)

`dxvk_limits.h` constants become: `MaxSharedPushDataSize = 64` (unchanged), `MaxPerStagePushDataSize = 256` (was 32), `MaxReservedPushDataSize = 32` (unchanged), `MaxTotalPushDataSize = 1376` (= 64 + 256*5 + 32; was 256).

Rationale: the FF VS transform block lives in the VS per-stage region. Its declared block offset is 64 (the SPIR-V member offset of the first mat4, after the 52 B render-state members, 16-aligned) and its size is 192 B, so a stage region must hold offset+size = 256 B. VS region = constantData[64, 320); block src = 64 (region base) + 64 (block offset) = 128, dst = 64.
