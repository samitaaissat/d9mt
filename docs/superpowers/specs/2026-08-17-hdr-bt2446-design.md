# HDR present pipeline for d9mt — BT.2446-A / ICtCp

Status: approved 2026-08-17. Target branch `feat/hdr-bt2446` off `wowsilicon` @ `5f7ae4d`.

## 1. Goal

Give d9mt the HDR output the user already tested and approved in **mtld3d**
(athei, v0.6.0, zlib). Concretely: on an EDR-capable display, present through an
`RGBA16Float` `CAMetalLayer` and route the LDR frame through ITU-R BT.2446
Method A inverse tone mapping operated in ICtCp, with the curve's peak following
the display's *live* headroom.

Secondary, explicitly requested: an optional PQ / HDR10 output mode. This is
**not** part of mtld3d parity — mtld3d never uses PQ — and is expected to look
different, because macOS applies its own PQ→display mapping.

Non-goal: widening the game's internal render targets. WoW 3.3.5a is
fixed-function plus simple `ps_2_0` against 8-bit sRGB source art; there is no
wider-range signal to recover, and RT format meddling in this driver has an
unexplained failure history (`pixelFormatView` narrowing shipped as payload v5
and was reverted in v6).

Out of scope for this spec: the shadow/render-pass performance pass. That is a
separate, independent workstream landing after this one.

## 2. What already exists, and what does not

The pinned winemetal (DXMT v0.80) already implements everything needed to
configure an HDR layer. d9mt calls none of it.

| Capability | Route | Status |
| --- | --- | --- |
| fp16 layer | `WMTLayerProps.pixel_format` → `MetalLayer_setProps` | available |
| extended-linear tag + `wantsExtendedDynamicRangeContent` | `MetalLayer_setColorSpace(WMTColorSpaceHDR_scRGB)` | available |
| PQ tag | `MetalLayer_setColorSpace(WMTColorSpaceHDR_PQ)` → `kCGColorSpaceITUR_2100_PQ` (`winemetal_unix.c:2112`) | available |
| EDR headroom read | `MetalLayer_getEDRValue` | **available but unsafe — see §3** |
| display's own colorspace ("passthrough") | none — `GetColorSpaceName` is a closed switch over four constants | **needs a new call** |
| `CAEDRMetadata` | absent from winemetal entirely | **needs a new call** |

Current SDR pinning, all in `src/d3d9fe/d9mt_presenter.cpp`:

| What | Value | Line |
| --- | --- | --- |
| layer `pixel_format` | `WMTPixelFormatBGRA8Unorm` | `:986` |
| proxy image format | `VK_FORMAT_B8G8R8A8_UNORM` | `:994` |
| proxy `colorSpace` | `VK_COLOR_SPACE_SRGB_NONLINEAR_KHR` | `:1014` |
| `supportsColorSpace()` | accepts `SRGB_NONLINEAR` only | `:860` |

**No winemetal rebuild anywhere in this design.** winemetal's PE half dispatches
through numeric indices baked into a prebuilt binary we ship verbatim; forking it
would mean staying index-compatible with DXMT forever. Both new entry points go
into **d9mtmetal**, our own unixlib, whose stated purpose is exactly "the entry
points winemetal lacks".

## 3. The safety finding that forces a new unixcall in phase 1

`_MetalLayer_getEDRValue` (`winemetal_unix.c:2275-2299`) walks
`layer.delegate → NSView → NSWindow → NSScreen` **on the calling thread**, with
no `execute_on_main`. `_WMTQueryDisplaySettingForLayer` (`:2351-2380`) does the
same unguarded walk. `NSView.window` and `NSWindow.screen` are main-thread-only.

This is mtld3d's own bug, fixed in commit `119c0db`: *"The submit thread crashed
in AppKit with a null dereference about three seconds after porting into a
raid."* A zone transition is precisely when the main thread rebuilds those
objects, and zone-ins and raids are this user's workload.

The failure would not present as a clean crash. Wine silently absorbs faults on
non-wine threads: the thread dies, no stderr, no `.ips`, and the process lives
on — a frozen render with a live process.

Therefore: the walk happens inside a `dispatch_async` to the main queue, in our
own unixlib, and the present thread only ever reads published statics. This is
mandatory, not an optimisation.

## 4. Design

### 4.1 Capability gate — one-shot

At `Presenter::recreateSwapChain`, before the first `nextDrawable`:

```
hdrActive = envEnabled
         && maximum_potential_edr_color_component_value > 1.0f
         && isfinite(potential)
```

`potential` is the **static panel ceiling** and is returned ungated by
`wantsExtendedDynamicRangeContent`, so it is readable before anything is
configured. The **dynamic** value reads `1.0` at attach and must never be used
for the gate — HDR would never engage.

Latched into a process-global atomic; never re-evaluated, including across
`Reset`. Measured on the target machine: `potential = 4.2686`, `dynamic = 1.0`.

Gate fails → layer stays `BGRA8Unorm`, proxy stays `B8G8R8A8_UNORM`, PSO key is
bit-identical to today, zero added work.

### 4.2 Layer and proxy configuration

Three writes that **must stay coupled** — the proxy→drawable copy at `:738-748`
is a same-format blit and a mismatch is a Metal validation abort:

1. `:986` layer `props.pixel_format` → `WMTPixelFormatRGBA16Float`
   (`getProps` → modify → `setProps`; `setProps` writes all fields).
   `framebuffer_only` stays `false`, `opaque` stays `true`.
2. `:994` proxy `info.format` → `VK_FORMAT_R16G16B16A16_SFLOAT`
   (already in the caps table at `d9mt_instance.cpp:146-147`, full `COLOR_STD`).
3. `:1014` proxy `info.colorSpace` → `VK_COLOR_SPACE_EXTENDED_SRGB_LINEAR_EXT`,
   and `:860` `supportsColorSpace` accepts it.

Then `MetalLayer_setColorSpace` — display-native extended-linearized via the new
d9mtmetal call (parity with mtld3d's `passthrough` default), falling back to
`WMTColorSpaceHDR_scRGB` if unavailable.

Assert at the end of `recreateSwapChain` that
`wmtFormatFor(proxy.format) == layerProps.pixel_format`.

### 4.3 Headroom polling

- PE side calls `D9MT_FUNC_LAYER_EDR` every 32 presents from `presentImage`
  (mtld3d's `HEADROOM_REFRESH_PRESENTS = 32`), counter seeded already-due so the
  first present refreshes.
- Native side returns the last published statics immediately, then fires a
  `dispatch_async` to the main queue that redoes the walk and republishes.
  Fire-and-forget; never `dispatch_sync` (that deadlocks). One outstanding block,
  bounded by an atomic flag.
- Published into `std::atomic<float> g_edrPeak`, seeded `1.0`. Two relaxed atomic
  reads per frame, one dispatch per 32 presents.
- Log headroom changes only past 5% drift.

**The shader receives the dynamic value, never the potential.** macOS globally
scales content exceeding the current EDR ceiling by `current/requested` — a peak
above live headroom dims the *entire image*, ~4× on this display.

### 4.4 Shader variants and PSO key

```cpp
enum class HdrMode : uint32_t { None = 0, Passthrough = 1, Bt2446 = 2, Bt2446Pq = 3 };

uint32_t key = uint32_t(dstFormat)                 // maxes at 236
             | (uint32_t(hdrMode)  << 28)          // bits 28-29, previously free
             | (pointFilter ? 0x80000000u : 0u)    // bit 31, unchanged
             | (useGamma    ? 0x40000000u : 0u);   // bit 30, unchanged
```

`getBlitPso` gains a defaulted `HdrMode hdrMode = HdrMode::None`, so
`DxvkContext::blitImageView` (`d9mt_context.cpp:3852`) is untouched.

Per-frame selection:

```cpp
HdrMode mode = !g_hdrActive.load()        ? HdrMode::None
             : (g_edrPeak.load() <= 1.0f) ? HdrMode::Passthrough
                                          : HdrMode::Bt2446;
```

**The passthrough short-circuit is mandatory.** BT.2446-A is *not* identity at
`L_hdr == L_sdr`: it maps mid-grey 21.4 nits → 15.4 nits, −28%. Without it every
frame before macOS promotes the screen is visibly crushed. A stale comment in
mtld3d (`macdrv.rs:1036`) claims otherwise; the shipped branch is authoritative.

Net PSO cache impact: **+2 entries**, 0 extra library compiles. The existing
present entry moves from `{BGRA8Unorm, None}` to `{RGBA16Float, None}`.

Also fix the pre-existing hole at `:259`: `ensureBlitFunctionsLocked`'s
early-return guard omits `s_blitPsPoint`. Add it plus the new handles to that
guard and to the completeness check at `:295`.

### 4.5 Uniform binding

`buffer(0)` is `d9mt_blit_params`, `buffer(1)` is the gamma ramp. HDR uniforms go
to **`buffer(2)`**, appended to the existing `wmtcmd_render_setbytes` chain in
`DxvkSwapchainBlitter::present` (`:1280-1290`) as a third link. Gamma and HDR are
mutually exclusive, so the chain never carries both.

16 bytes, recomputed per present:

```cpp
float peak       = g_edrPeak.load(std::memory_order_relaxed);
float lHdrNits   = peak * 100.0f;
float pHdr       = 1.0f + 32.0f * std::pow(lHdrNits / 10000.0f, 1.0f / 2.4f);
float log2PHdr   = std::log2(pHdr);
float invPMinus1 = 1.0f / (pHdr - 1.0f);
```

### 4.6 Gamma-ramp ordering

`useGamma = (m_gammaCpCount != 0 && !bs.gammaRamp.empty()) && hdrMode == HdrMode::None;`
— one line at `:1103`. HDR wins, matching DXMT (`dxmt_command.metal:326`).

Dead code in production: DXVK forwards ramps only when `!Windowed`
(`d3d9_swapchain.cpp:731-734`) and `ConfigService.swift:39-41` writes
`gxWindow=1` unconditionally. Added anyway because tone-map→gamma is actively
destructive: the LUT's `clamp(int3(index),0,255)` hard-clips every EDR highlight
back to 1.0.

### 4.7 Load action

When `hdrMode != None`, force `pass.colors[0].load_action = WMTLoadActionClear`
with `{0,0,0,1}` even on the `fullDst` path (currently `DontCare` at `:1224`).
Undefined float memory reads as magenta noise; mtld3d hit this three separate
times (`4240109`, `e6171d9`, `08e56e8`). A tile-GPU fast clear is ~free. SDR keeps
`DontCare` so that path stays bit-identical.

### 4.8 Structural advantage over mtld3d

d9mt's present **already** runs a fullscreen-triangle sample pass: WoW's
`D3DFMT_X8R8G8B8` backbuffer carries an RGB1 `packedSwizzle`, which fails the
blit-encoder fast-path guard at `:1189`. So the tone map adds **zero passes**.
mtld3d has to add a dedicated present pass.

## 5. The curve

Ported verbatim from `mtld3d/unix/unix/src/metal/present.msl` (verified against
the file directly, not via summary). Key constants:

```
L_SDR      = 100.0            // Apple anchors 1.0-in-drawable to 100 nits
P_SDR      = 5.4395284707f
LOG_P_SDR  = 1.6937747f       // natural log
```

Pipeline: sRGB EOTF (IEC 61966-2-1 piecewise, not `pow(x,2.2)`) → `× L_SDR` →
BT.709→LMS → PQ OETF → ICtCp → BT.2446-A luminance inversion (three-segment) →
chroma scaled by `i_ratio = i_hdr / max(i_in, 1e-6)` → ICtCp→LMS-PQ → PQ EOTF →
LMS→BT.709 → `max(·, 0)` → `/ L_SDR`.

The three-segment inversion inverts BT.2446-A's forward piecewise:

```
Y'c = 1.0770 Y'p                            for Y'p <= 0.7399
Y'c = -1.1510 Y'p^2 + 2.7811 Y'p - 0.6302   for 0.7399 < Y'p < 0.9909
Y'c = 0.5 Y'p + 0.5                         for Y'p >= 0.9909
```

The literal `4.83307641 - 4.604*Y'c` is the discriminant
`2.7811^2 - 4*1.1510*(0.6302 + Y'c)`; the minus root is correct because the
parabola's vertex (`Y'p = 1.2081`) lies right of the segment's domain.

**Two deliberate deviations from spec, preserved for look-parity:**

1. `P_SDR = 5.4395284707` does not match its own formula, which evaluates to
   `5.6969576564` at `L_SDR = 100` (the literal corresponds to ~87.35 nits paper
   white) and `LOG_P_SDR` is not exactly `ln(P_SDR)` (`= 1.6936924`). The shipped
   pair runs 2–5% darker through the midtones. **These are the tested look.**
2. mtld3d's Rust doc comments say chroma is untouched; the shipped MSL scales
   `Ct`/`Cp` by `i_ratio`. **The MSL is the tested artifact.**

`D9MT_HDR_CURVE=spec` exposes the corrected pair for measurement. Default is
`mtld3d`.

**Matrix hazard:** the LMS-PQ↔ICtCp pair must both be the `/4096` form. A
`/8192` forward against a `/4096` inverse halves chromatic deltas — invisible on
grey (`Ct=Cp=0`), catastrophic on saturated content. This was a shipped bug in
mtld3d.

Expected transfer at `peak = 4.2686` (`L_hdr = 426.86`): sRGB `0.05→0.64`,
`0.20→6.15`, `0.50→47.8`, `0.75→135.8`, `0.90→257.1`, `1.00→426.6` nits.

## 6. New d9mtmetal entry points

`enum d9mt_unix_func` runs 0–5 with `D9MT_FUNC_COUNT` as terminator. **Append
immediately before `D9MT_FUNC_COUNT`** — existing indices preserved. Extend
*both* `__wine_unix_call_funcs[]` and `__wine_unix_call_wow64_funcs[]`
(`unix.m:857-877`); both are sized by `D9MT_FUNC_COUNT` and must stay equal
length. Params structs obey the header ABI rule: fixed-width fields, pointers as
zero-extended `uint64_t`, explicit padding.

`dll.c` needs **zero** changes — `D9MT_UnixCall(code, params)` is code-agnostic.

| Code | Purpose |
| --- | --- |
| `D9MT_FUNC_LAYER_EDR = 6` | main-queue EDR walk + publish (§3, mandatory) |
| `D9MT_FUNC_LAYER_COLORSPACE = 7` | display-native `CGColorSpaceCreateExtendedLinearized` (parity with mtld3d `passthrough`) |
| `D9MT_FUNC_LAYER_EDR_METADATA = 8` | `CAEDRMetadata` — only if PQ is pursued with mastering metadata |

```c
struct d9mt_layer_edr_params {
  uint64_t layer;             /* in:  CAMetalLayer handle                */
  float    max_edr;           /* out: live headroom, or 1.0              */
  float    max_potential_edr; /* out: static panel ceiling, or 1.0       */
  uint32_t refresh;           /* in:  1 = also queue a main-queue re-read */
  uint32_t padding;
};
```

### ABI handshake (skew safety)

`__wine_unix_call` indexes the table with **no bounds check**, so a new
`d3d9fe.dll` against an older `d9mtmetal.so` would jump through whatever follows
entry 5. Probing by "call the new code and check NTSTATUS" *is* the crash.

Handshake through an index that **already exists**:
`d9mt_newlibrary_params` has an unused `uint32_t padding`, and the PE side
already zero-initialises the struct and calls `D9MT_FUNC_NEW_LIBRARY_FROM_SOURCE`
once at blitter init.

- Rename the field `abi_func_count` (out).
- New `.so` writes `D9MT_FUNC_COUNT`; old `.so` never touches it → stays 0.
- PE caches it; gate every new code on
  `g_d9mtmetalFuncCount > D9MT_FUNC_LAYER_EDR`, else `hdrActive = false`.

An out-of-range index is never dispatched; an old `.so` degrades to plain SDR.
The payload already ships `d3d9.dll` + `d3d9fe.dll` + `d9mtmetal.{dll,so}`
atomically under one `.sha256` — that is the real-world guard; the handshake is
the belt.

## 7. Config surface

d9mt has no `.conf` parser; it uses `getenv("D9MT_*")`, which is also what
WoWSilicon's `LaunchService` controls.

| Key | Values | Default (test drop) |
| --- | --- | --- |
| `D9MT_HDR` | `0` / `1` / `auto` | **`0`** |
| `D9MT_HDR_COLORSPACE` | `display` / `scrgb` / `pq` | `display` |
| `D9MT_HDR_CURVE` | `mtld3d` / `spec` | `mtld3d` |
| `D9MT_HDR_PEAK` | float nits override, `0` = live | `0` |

`auto` = engage whenever `potential > 1.0` (mtld3d's shipped behaviour). Ship the
first build at `0` so the user A/Bs by relaunching and a regression cannot cost a
raid night. Flip to `auto` once parity is signed off. One startup log line per
resolved key.

A WoWSilicon launcher toggle (`GraphicsSettings.hdrEnabled`, `decodeIfPresent`
default `false`, plus a `ModelCompatibilityTests` case) lands **after** parity is
confirmed, not before.

## 8. Verification

Delivery stops at built + installed into the live game dir. **Nothing is uploaded
to a GitHub release** — uploading `d9mt-<N>.tar.gz` to `runtime-v1` is shipping,
because `RuntimeUpdateService` auto-adopts the highest `N` within 24h with no
gate.

Per the user's decision, verification is **synthetic until the very end**; the
real client is booted once for visual sign-off.

Synthetic, no game, no display:

1. Curve conformance at `peak = 4.2686` against the transfer table in §5,
   tolerance 0.5%.
2. Neutral preservation: white `(1,1,1)` → `(426.47, 426.72, 426.72)` nits,
   within 0.1%.
3. Gamut clip envelope: saturated red → `(238.31, −5.37, −1.16)`, green →
   `(−33.11, 336.28, −12.96)`, blue → `(0.72, −3.12, 166.64)`. Regression trap
   for a mismatched ICtCp matrix pair.
4. Matrix round-trips: `M_LMS_TO_BT709 · M_BT709_TO_LMS` within 7.4e-4 of
   identity; `M_LMS_PQ_TO_ICTCP · M_ICTCP_TO_LMS_PQ` within 3.4e-5. The second
   is what catches a `/8192` vs `/4096` mix.
5. Passthrough non-identity guard: BT.2446 at `L_hdr = 100` maps sRGB 0.5 →
   15.41 nits, **not** 21.4. Encodes the −28% so nobody "simplifies" the
   short-circuit away.
6. GPU-side agreement: a host Metal tool compiles the *same* MSL, renders a
   256-step ramp to offscreen `RGBA16Float`, reads back, diffs against the CPU
   harness within 1e-3. Catches `fast_math` and MSL `select()` surprises.
7. PSO-key invariance: with `hdrMode == None` the key is bit-identical to today.
8. `depthbias`, `resettest`, `consttest`, `capstest` stay green. These are wine
   PE test exes, so they need the bundled runtime and a throwaway `WINEPREFIX` —
   and an **unsandboxed shell**, because the agent sandbox blocks `ptrace` and
   the x87 loader dies with `PT_THUPDATE failed`. A prefix bootstrapped under a
   sandboxed shell is poisoned and must be wiped. Items 1–7 are host-native and
   have no such constraint.

Final, with the real client (single session):

9. Layer promotion, headroom `1.00 → 4.27` within ~32 presents, no magenta frame
   at startup / `Reset` / alt-tab / resolution change.
10. Frame-time delta vs `D9MT_HDR=0`. Budget: well under 1 ms at 3440×1440 —
    ~30 transcendentals/pixel in a pass that already exists.
11. A/B against mtld3d. Both are installed in the same prefix, so this is a
    relaunch. Confirm both report the same `L_hdr` first — if they disagree the
    bug is in the polling, not the shader. Then fixed camera, fixed time of day,
    display brightness untouched (headroom moves with brightness).
12. User verdict on the look.

## 9. Risks

| Risk | Severity | Mitigation |
| --- | --- | --- |
| AppKit crash from the unguarded `view→window→screen` walk on a zone transition; may present as a frozen render because Wine absorbs foreign-thread faults | Critical | §3 — main-queue `dispatch_async` only; never call `MetalLayer_getEDRValue` directly |
| Layer/proxy format flip applied to one of the pair → cross-format copy, Metal abort | Critical | Keep `:986`/`:994` adjacent with a coupling comment; assert at end of `recreateSwapChain` |
| `WMTColorSpaceSRGBLinear` chosen instead of `HDR_scRGB` → EDR never enabled, port silently does nothing | High | Hard-code the HDR enum; warn loudly if headroom never leaves 1.0 while `potential > 1.0` |
| Magenta frames from undefined fp16 memory | High | §4.7 `LoadActionClear`; never begin the pass if PSO creation failed |
| Look mismatch because mtld3d's tested default was `passthrough` | High | Ship the display-colorspace call in phase 1 rather than deferring it |
| Crushed early frames if the passthrough short-circuit is dropped | Medium | Synthetic assertion 5 encodes the −28% as a test |
| Unixlib skew into a bounds-check-free dispatch | Medium | §6 handshake through an existing index; atomic payload install |
| Perf regression from the added transcendentals | Medium | `fast_math` already pinned; pass already exists; `D9MT_HDR=0` is a zero-cost escape hatch |
| Source view turns out to be an `_sRGB` format view → double decode | Medium | Resolve before shader work; if true, drop the EOTF from the fragment |
